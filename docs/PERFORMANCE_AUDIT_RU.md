## Обозначения, границы анализа и метод

- `N` — число вершин **внутреннего** C++ `Graph`, `M` — число сохранённых рёбер, включая повторы; `d` — размерность раскладки; `f` — размерность после проекции. CLI выдаёт `f=2` или `f=3`.
- `T` — число итераций FaR; `C` — число камер BestView; `R` — число запусков серии; `B` — число обращений к результатам по `run`.
- `A` — число пар рёбер с общей вершиной. Для простого графа без петель `A = Σ_v binom(deg(v), 2)`. Оговорки о петлях и кратных рёбрах существенны для C8.
- `D` — размер всего входного JSON; `b` — размер выбранной записи графа; `J` — размер выходного JSON одной раскладки. Для оценок по байтам считаем длины числовых записей ограниченными; иначе добавляется стоимость записи/сравнения самих строк.
- `W` — число столбцов DataFrame; `k` — число нужных метрик, сейчас не более 10, а для камер — 4. `s` — число точек на дуге, сейчас по умолчанию 80.
- `E` — суммарная длина stderr серии; `ℓ` — верхняя граница длины сравниваемой строки ошибки; `Z` — суммарное число найденных строк для запросов к неуникальному `run`.
- `Q₂` — время одного полного `computeMetrics` в 2D: `Θ(N+M+N²+M²+NM)` при `N≥2`. Разложение сохраняет смысл отдельных циклов, хотя `NM ≤ (N²+M²)/2`.

## C++: путь выполнения и подробности

[main](/Users/user/Code/Repos/GraphDrawing/src/app/artist.cpp:21) выполняет цепочку `readGraphByName → InitialPlacement → Layout → Projection → computeMetrics → writeEmbeddingJson`. У `kleinBestView` внутри Projection находится дополнительный цикл расчёта метрик. Именно он многократно усиливает накладные расходы Metrics.

Для FaR и 2D-выхода общая оценка имеет вид `Θ(D+N+M+Nd+V(d)+Td(N²+M+N)+P+Q₂+J)`, где `V(d)` — вызов объёма border policy, а `P` — работа проекции. Для простого orthogonal `P=Θ(Nf)`, для kleinOrthogonal `P=Θ(Nd)`, для BestView `P=Θ(CNd+CQ₂)`; фактически последний содержит `4C` полных расчётов Metrics. В `default` величина `V(d)=O(1)`, в гиперболическом `poly` сейчас `Θ(d³)`.

После C1–C4 у BestView сохраняется квадратичная по размерам графа оценка, но внутри неё остаётся один расчёт Metrics на камеру, а память координат кандидатов теряет множитель `C`. Отдельно `V(d)` становится линейной. Для random-layout итерационный член FaR отсутствует; два последовательных заполнения координат обсуждаются в C12. Неактивный `computeLayoutEuclideanOld` не использовался для оценки текущего CLI-пути.

### C1. Общий определитель для заведомо диагонального Gram

**Код:** [HyperbolicSpace::volume](/Users/user/Code/Repos/GraphDrawing/src/spaces/HyperbolicSpace.cpp:167), [tangentToDefault](/Users/user/Code/Repos/GraphDrawing/src/spaces/HyperbolicSpace.cpp:64), [determinantBareiss](/Users/user/Code/Repos/GraphDrawing/src/spaces/Space.cpp:11). Для сравнения: [EuclideanSpace::volume](/Users/user/Code/Repos/GraphDrawing/src/spaces/EuclideanSpace.cpp:68) уже использует диагональную структуру.

Создаются `d` векторов длины `d` с единственной ненулевой координатой, затем `d×d` Gram. Каждая ячейка требует трёх `tangentNorm`, каждый из которых проходит по `d` координатам и создаёт временный вектор. Заполнение стоит `Θ(d³)`. Bareiss добавляет ещё `Θ(d³)` и копию матрицы `Θ(d²)`, поскольку получает её по значению.

Здесь можно упростить **ровно текущую формулу**, не меняя модель объёма. В точке `origin=0` временная координата касательного вектора равна нулю. Поэтому текущая лоренцева норма касательного вектора становится евклидовой. Для осевых векторов `e_i = side_i·basis_i`:

`Gram_ij = 0` при `i≠j`, `Gram_ii = side_i²`.

Следовательно, `sqrt(det Gram) = ∏_i |side_i|`. Это один проход `Θ(d)` с `O(1)` дополнительной памятью. Вся формула должна оставаться в `HyperbolicSpace`, Metrics по-прежнему вызывает `space.volume`.

Этот вызов выполняется один раз перед FaR при `borderPolicy=poly`. При `default` метод `domainVolume` возвращает `-1`, так что кубическая стадия отсутствует. В актуальном ноутбуке с перебором размерностей и `poly` проблема активна.

Результат математически эквивалентен существующей формуле; побитовая эквивалентность не обещается: старый путь содержит квадратные корни, вычитания близких чисел, пороги Bareiss и потенциальные переполнения. Это также не утверждение, что произведение сторон является точным гиперболическим объёмом координатной области: здесь оптимизируется определённый в проекте расчёт.

### C2. Четыре полных расчёта метрик на одну камеру

**Код:** [вложенные циклы по метрикам и камерам](/Users/user/Code/Repos/GraphDrawing/src/projections/KleinProjection.cpp:85), [финальный расчёт в main](/Users/user/Code/Repos/GraphDrawing/src/app/artist.cpp:52).

Внешний цикл проходит по четырём индексам метрик. Внутри для каждой камеры заново создаётся `Embedding`, а `computeMetrics` вычисляет **весь** набор. Затем `metricValue` извлекает одно поле и остальные результаты теряются.

При стандартных 1000 камерах это 4000 полных расчётов внутри проекции и ещё один в `main`. Достаточно один раз получить `Metrics` для каждой камеры, сохранить четыре используемых значения и отдельно выполнить ту же нормализацию по каждому столбцу. Получатся 1000 внутренних расчётов и один финальный. Порядок `Θ(CQ₂)` сохраняется, но это очень крупная устранимая константа.

Нормализация использует минимум и максимум **по всем** кандидатам: выбирать победителя по ещё не нормализованным текущим значениям нельзя. Нужно сохранить порядок кандидатов, добавление вклада константной метрики и правило разрешения ничьей: первый максимум через `>`.

Особый случай `C=1`: единственный кандидат всегда ортогональный, все четыре значения при нормализации константны. Внутренний scoring вообще не нужен; достаточно проекции и обычного финального `computeMetrics` в `main`. При `C>1` отключение ненужных для scoring полей само по себе не убирает основные квадратичные циклы: используемые четыре метрики всё равно задействуют пары вершин, пары рёбер и вершина–ребро.

### C3. Все координаты всех камер одновременно в памяти

**Код:** [cameras и candidates](/Users/user/Code/Repos/GraphDrawing/src/projections/KleinProjection.cpp:71), [повторное проецирование победителя](/Users/user/Code/Repos/GraphDrawing/src/projections/KleinProjection.cpp:113).

`candidates` хранит `C` самостоятельных массивов по `N` точек. Память координат равна `Θ(CNf)`, дополнительно есть `Θ(Cd)` на камеры и `Θ(C)` на оценки. Для `vector<vector<ld>>` сюда добавляются `Θ(CN)` объектов внутренних векторов и их аллокаций.

Совместно с C2 можно генерировать одну камеру, проецировать один временный набор координат, вычислять его метрики и освобождать координаты. Достаточно хранить камеры и четыре числа на каждую. После выбора победителя его проекция строится ещё раз — код уже делает такой заключительный проход.

Память кандидатов станет `Θ(Nf+Cd+C)`. Время останется `Θ(CNd+CQ₂)`; повторного расчёта метрик для поиска победителя не требуется. Более сложный вариант — восстановление камер повторным воспроизведением RNG, чтобы убрать хранение `Cd`, но для первого исправления это излишне.

Это оценка памяти **кандидатов**. Исходные координаты `Θ(Nd)`, топология `Θ(N+M)` и рабочая память одного расчёта метрик никуда не исчезают.

### C4. `auto` снимает ссылки и копирует большие структуры

**Код:** [начало computeMetrics](/Users/user/Code/Repos/GraphDrawing/src/metrics/Metrics.cpp:10), [ссылочные getters](/Users/user/Code/Repos/GraphDrawing/src/core/Embedding.cpp:59), [поля Graph](/Users/user/Code/Repos/GraphDrawing/src/core/Graph.h:31).

Три строки `auto graph = emb.getGraph()`, `auto edges = graph.edges()`, `auto pts = emb.getCoords()` создают копии. Первая копирует и список смежности, и `_edges`; вторая снова копирует список рёбер; третья глубоко копирует все координатные векторы.

Это `Θ(N+M+Nf)` лишнего времени и памяти **на вызов**, хотя функция ничего в них не меняет. Получение `const auto&` либо использование существующего `getEdges()` стоит `O(1)`. Граф принадлежит вызывающему коду и живёт дольше Metrics; новую модель владения вводить не нужно.

При BestView лишний объём копируемых данных сейчас умножается на `4C`. Пиковая память не умножается на `4C`, поскольку вызовы последовательные. Удаление только этих копий оставляет у текущей Metrics `O(f)` рабочей памяти для небольших векторов, если отдельно не добавлять кеши C8–C10.

В 3D блоки пересечений, углов и вершина–ребро пропускаются, но копия графа всё равно выполняется. Поэтому текущая 3D Metrics стоит `Θ(Nf+N²f+N+M)`, а после ссылок исчезает зависимость от `M` из чтения топологии. Для мультиграфа с очень большим `M` это может менять доминирующий член, а не только константу.

### C5. Промежуточные координаты копируются вместо передачи владения

**Код:** [fitToFigSize](/Users/user/Code/Repos/GraphDrawing/src/projections/Projection.cpp:60), [OrthogonalProjection](/Users/user/Code/Repos/GraphDrawing/src/projections/OrthogonalProjection.cpp:26), [конструктор Embedding](/Users/user/Code/Repos/GraphDrawing/src/core/Embedding.cpp:13), [IdentityProjection](/Users/user/Code/Repos/GraphDrawing/src/projections/IdentityProjection.cpp:26), [PoincareProjection](/Users/user/Code/Repos/GraphDrawing/src/projections/PoincareProjection.cpp:46).

Ортогональная проекция сначала создаёт `res`, затем `fitToFigSize` копирует его в собственный массив, а конструктор `Embedding(const Graph&, const vector<Pt>&)` копирует результат ещё раз. Аналогичная заключительная копия есть в остальных проекциях. `std::move(f)` в возвращаемом `ProjectionResult` уже полезен, но он не отменяет копию, произошедшую при создании `f`.

Минимальное направление: разрешить `fitToFigSize` работать с уже принадлежащим проекции буфером и добавить передачу владения готовым массивом в `Embedding`, сохранив существующий копирующий API для случаев, когда он нужен. Передача самого `vector` с обычным аллокатором стоит `O(1)`, тогда как построение и заполнение координат всё равно требует `Θ(Nf)`.

Для identity хотя бы один новый массив нужен при текущем контракте неизменяемого входного `Embedding`: преобразование масштаба меняет точки. Для orthogonal достаточно одного выходного массива и малых векторов границ. Уже исправленное пользователем получение точки по ссылке повторно исправлять не требуется: ортогональная проекция теперь не копирует все `d` координат ради первых `f`.

### C6. Много выделений памяти внутри неизбежного перебора FaR

**Код:** [основной цикл FaR](/Users/user/Code/Repos/GraphDrawing/src/layouts/FruchtermanAndReingold.cpp:72), [операторы Pt](/Users/user/Code/Repos/GraphDrawing/src/core/template.h:81), [setPos](/Users/user/Code/Repos/GraphDrawing/src/core/Embedding.cpp:21), [DefaultBorderPolicy::normalizePoint](/Users/user/Code/Repos/GraphDrawing/src/borderPolicy/BorderPolicy.cpp:31).

Каждая операция `Pt / scalar` и `Pt * scalar` создаёт новый `vector`. Поэтому `disp[i] -= v1 / v1N * f_r(v1N)` выполняет два дополнительных прохода по `d` координатам и два выделения памяти перед накоплением. Таких выражений `Θ(T(N²+M))`. Для `step` повторяется тот же шаблон. Затем default-нормализация копирует точку без изменений, а `setPos` ещё раз копирует её содержимое.

Накопление масштабированного вектора можно выполнять одним проходом непосредственно в `disp`, сохраняя формулы геометрии внутри Space. В частности, вычисление `(v[c]/norm)*force` внутри одного прохода убирает временные массивы без обязательной перестановки скалярных операций. Объединение коэффициента в `force/norm` — дополнительное изменение порядка округления, которое стоит проверять отдельно.

`disp` создаётся заново в каждой итерации как `N` отдельных векторов. Его можно выделить один раз и обнулять между итерациями. Аллокаций будет `Θ(N)` вместо `Θ(TN)`, но обнуление по-прежнему стоит `Θ(TNd)`: писать в отчёте об ускорении этой стадии до `Θ(Nd)` было бы неверно.

Передача готовой позиции во владение `Embedding` убирает копирование элементов, но не обязательно сама по себе даёт лучший allocator-профиль: старый буфер позиции тоже нужно освобождать. Это локальная оптимизация для измерения вместе с повторным использованием буферов. Общая сложность FaR остаётся `Θ(Td(N²+M+N))`, никакая замена алгоритма отталкивания не предлагается.

### C7. Одни и те же данные точек и пар вычисляются заново

**Код:** [два направления logMap и нормы](/Users/user/Code/Repos/GraphDrawing/src/layouts/FruchtermanAndReingold.cpp:75), [HyperbolicSpace::lift](/Users/user/Code/Repos/GraphDrawing/src/spaces/HyperbolicSpace.cpp:29), [logMap](/Users/user/Code/Repos/GraphDrawing/src/spaces/HyperbolicSpace.cpp:98), [tangentToDefault / tangentNorm](/Users/user/Code/Repos/GraphDrawing/src/spaces/HyperbolicSpace.cpp:64).

В пределах одной итерации позиции не меняются до завершающего прохода. Однако гиперболический `logMap(a,b)` поднимает обе точки на гиперболоид, а `logMap(b,a)` заново делает то же самое и пересчитывает симметричный скаляр `alpha` и расстояние. Далее `tangentNorm` снова восстанавливает временную компоненту. В `tangentToDefault` выражение `norm(at) * norm(at)` содержит два одинаковых вызова нормы.

Для пары, являющейся ребром, направленные векторы и нормы сначала вычисляются при отталкивании, затем повторяются в притяжении. Можно подготовить данные точек один раз на итерацию и переиспользовать симметричные величины внутри парной операции Space. Подготовка данных точек тогда стоит `O(TNd)` вместо повторений внутри `O(T(N²+M))` обращений. Векторные произведения для различных пар по-прежнему требуют `Θ(T(N²+M)d)`.

Даже без кеша всех точек `HyperbolicSpace::tangentNorm` может вычислить текущую формулу `sqrt(max(||v||² - (at·v)²/(1+||at||²), 0))` через скалярные суммы без временного `Pt` размерности `d+1`. Это та же метрика; формула должна оставаться в `HyperbolicSpace`. Проверка численной устойчивости нужна около предельных значений.

Нельзя в общем случае заменить `logMap(b,a)` на `-logMap(a,b)`: это векторы в разных касательных пространствах. Для Euclidean такое упрощение допустимо внутри соответствующей реализации. Если кешировать данные рёбер между двумя проходами, достаточно `O(Md)` памяти; таблица для всех `N²` пар не нужна. Кеш инвалидируется после обновления координат. У повторных рёбер должны сохраниться кратность вклада и порядок суммирования, если нужна максимальная воспроизводимость.

### C8. Один угол считается дважды; инцидентность ищется глобально

**Код:** [angle](/Users/user/Code/Repos/GraphDrawing/src/metrics/Metrics.cpp:63), [ветви общих концов](/Users/user/Code/Repos/GraphDrawing/src/metrics/Metrics.cpp:120), [Graph::neighbors](/Users/user/Code/Repos/GraphDrawing/src/core/Graph.cpp:33).

Для общей поддержки потребуется сохранить идентичность экземпляров рёбер и текущие правила. Без этого оценка через `Σ binom(deg,2)` применима только к простым графам.

### C9. Пересечения: повторная конвертация концов и heap для 2D-разностей

### C10. Подготовка ребра повторяется `N` раз

**Код:** [is_pt_on_seg и pt_to_seg](/Users/user/Code/Repos/GraphDrawing/src/metrics/Metrics.cpp:86), [вложенный цикл ребро–вершина](/Users/user/Code/Repos/GraphDrawing/src/metrics/Metrics.cpp:139).

Для фиксированного ребра при каждой вершине повторяются `ab`, `ba`, проверка вырожденности, коэффициенты прямой и её нормирующая длина. Более того, часть разностей строится сначала в `is_pt_on_seg`, затем снова в `pt_to_seg`. Зависит от вершины только часть этих выражений.

Подготовка одного ребра перед внутренним циклом переносит `Θ(MN)` вычислений инвариантов в `Θ(M)`. Общее количество расстояний остаётся `Θ(MN)`. Поскольку обход уже идёт по рёбрам, хранить подготовку для всех `M` сразу не обязательно: достаточно одного подготовленного ребра и `O(1)` дополнительной памяти в 2D.

Если расстояние стало **ровно нулём**, дальнейшее уменьшение невозможно: можно закончить именно блок `minEdgeVertexDist`, продолжив остальные метрики. Худший случай остаётся `Θ(MN)`; на входе с ранним попаданием вершины на ребро работа блока сокращается до места первого нуля. Нельзя просто выйти из всей `computeMetrics`, поскольку расстояния между вершинами ещё не посчитаны. Замена точного нуля на `≤ EPS` дополнительно меняет результат и требует отдельного решения.

Сейчас формулы этой метрики уже находятся в Metrics и используют прямые 2D-отрезки даже для Poincaré. Оптимизированную реализацию следует поместить в API Space с явно сохранённой текущей семантикой. Переход к истинному расстоянию до гиперболической дуги — самостоятельное изменение математической модели, не оптимизация того же результата.

### C11. Читатель удерживает весь датасет дважды в разных представлениях

**Код:** [readFileToString](/Users/user/Code/Repos/GraphDrawing/src/io/JsonGraphReader.cpp:15), [парсинг и поиск записи](/Users/user/Code/Repos/GraphDrawing/src/io/JsonGraphReader.cpp:119), [два прохода по рёбрам](/Users/user/Code/Repos/GraphDrawing/src/io/JsonGraphReader.cpp:82).

Кеш parsed-пар убирает повторный разбор ценой `Θ(M)` памяти, но два последовательных прохода уже линейны. Поэтому это второстепенная часть C11, а не самостоятельная асимптотическая проблема. При потоковом построении можно организовать однократный разбор без отдельного кеша, аккуратно сохранив определение числа вершин.

Ускорение серии по времени за счёт однократной обработки датасета описано в P1. Эти эффекты относятся к одной границе Python/C++ и не должны суммироваться как независимые ускорения.

## Python: путь выполнения и подробности

Актуальная экспериментальная цепочка: `compileGd` при подготовке, затем `runTests → runTest → subprocess C++ → json.load → DataFrame`, далее `scoreRuns / bestRun / plotMetrics` и выбранные `renderRun → render.py → PNG`. Генерация датасета находится отдельно в `gen.py`; 3D-рендер доступен через `render3d.py`, а `renderRun` сейчас всегда запускает 2D-скрипт.

Для одинаковых по размеру входов само накопление серии имеет стоимость `Σ_r T_cpp(r) + Θ(RJ+RW)` плюс обработка флагов и захваченного stdout/stderr. При этом `RD` уже находится внутри суммы C++ запусков: второй раз прибавлять его как отдельную Python-работу нельзя. `runTests` не делает scoring и рендер автоматически — их затраты возникают только при соответствующих последующих вызовах.

### P1. Одни и те же байты датасета разбираются в каждом C++ subprocess

**Код:** [цикл runTests](/Users/user/Code/Repos/GraphDrawing/gd_experiments.py:325), [запуск процесса](/Users/user/Code/Repos/GraphDrawing/gd_experiments.py:222), [ноутбук с сериями по размерности](/Users/user/Code/Repos/GraphDrawing/testing/metrics_from_dim.ipynb), кодовые ячейки 8 и 10.

Каждый запуск получает прежний `--dataset`, поднимает новый процесс и заново читает весь JSON. Для `R` экспериментов над одним графом это `Θ(RD)`, хотя неизменный входной граф один и тот же. Кеш дисковой ОС может убрать физическое чтение, но не повторный JSON-разбор и построение объектов.

Относительно малое изменение без нового C++ сервера: один раз прочитать датасет в Python, сохранить выбранную запись в отдельный временный JSON-массив совместимого формата и использовать его во всей серии. Чтение станет `Θ(D+Rb)`, включая построение того же графа каждый раз. Для серии с разными графами — `O(D+Σ_r b_r)` при однократной подготовке записей; кеш должен учитывать путь и изменение датасета.

Долгоживущий C++ batch-режим способен дополнительно переиспользовать `Graph`, но это уже заметное расширение интерфейса. В исходных результатах следует сохранять достаточную информацию для воспроизведения, включая исходный датасет, выбранный граф и реально переданные флаги. Повторные имена графов должны разрешаться так же, как сейчас — первая подходящая запись.

Это оптимизация повторной подготовки **входа**. Не предлагается сокращать число экспериментов или менять FaR. На датасете из одного графа, где `b≈D`, выигрыш по порядку этой стадии отсутствует. Если сохранено требование валидировать весь файл перед серией, предварительная подготовка должна действительно разобрать весь исходный JSON.

### P2. Для строки из метрик создаются Python-объекты всех координат и рёбер

**Код:** [runTest: json.load и извлечение metrics](/Users/user/Code/Repos/GraphDrawing/gd_experiments.py:228), [формат C++ output](/Users/user/Code/Repos/GraphDrawing/src/io/EmbeddingWriter.cpp:48).

Это улучшение памяти, не `O(k)` времени. C++ запись полного output и хранение всех JSON на диске также останутся `Θ(RJ)`, пока не введён отдельный режим сохранения артефактов.

### P3. Квадратичное накопление ошибок ради первых трёх сообщений

**Код:** [failedRunsMessage](/Users/user/Code/Repos/GraphDrawing/gd_experiments.py:488).

Уникальные последние непустые строки добавляются в список `errors`, а условие `line not in errors` сканирует список. При `R` разных ошибках получается `R(R−1)/2` сравнений. Дополнительно stderr разбивается и фильтруется, что стоит `O(E)`. Верхняя оценка с длиной строк — `O(E+R²ℓ)`.

На выходе используются только `errors[:3]`. Поэтому достаточно сохранять до трёх уникальных строк и прекратить их сбор после третьей. Даже без hash set размер проверяемого списка ограничен тремя: весь метод имеет `O(R+E)` времени с учётом проверки return codes и обработки строк. Порядок первых трёх сообщений сохранится. Если когда-нибудь понадобится полный перечень, следует использовать set для membership и отдельный список для порядка; тогда оценка будет линейной в среднем по хешированию.

Ветвь включается только когда **все** запуски неуспешны. При одинаковой ошибке на всех запусках список имеет длину один и квадратичности нет. Поэтому влияние на успешные исследования нулевое, несмотря на настоящее улучшение худшего случая.

### P4. Повторные запросы по `run` превращаются в `B×R` сканирований

**Код:** [setImageScore](/Users/user/Code/Repos/GraphDrawing/gd_experiments.py:382), [renderRun](/Users/user/Code/Repos/GraphDrawing/gd_experiments.py:404).

Обе функции создают булев массив `df['run'] == run` длины `R`. Для одной ручной оценки это малый линейный проход; для обработки всех строк по очереди — `Θ(R²)` суммарно. Накладная память каждого поиска — `Θ(R)` на маску.

Один раз построенный индекс `run → позиции строк` даёт `O(R)` подготовки и ожидаемое `O(1)` нахождение ключа, плюс обработку совпадений. Для `B` запросов это `O(R+B+Z)`. В обычной таблице `runTests` номера уникальны, поэтому `Z≤B` и получается `O(R+B)`.

Необходимо сохранить разную семантику: `setImageScore` сейчас обновляет **все** совпадения, а `renderRun` требует ровно одно. Также API принимает произвольный DataFrame: нельзя безусловно использовать строку `run−1` после фильтрации/конкатенации. Индекс нужно либо строить для пакетной операции, либо явно обслуживать при изменении столбца `run`; не следует создавать скрытый потенциально устаревающий глобальный кеш.

### P5. Сотни маленьких DataFrame вместо одной таблицы

**Код:** [return pd.DataFrame одной строки](/Users/user/Code/Repos/GraphDrawing/gd_experiments.py:248), [накопление и concat](/Users/user/Code/Repos/GraphDrawing/gd_experiments.py:325).

`runTest` создаёт полноценный DataFrame на одну строку. `runTests` меняет его столбец `run`, сохраняет все такие объекты и в конце объединяет их. Сложность уже линейная по размеру результата `Θ(RW)`, потому что `concat` вызывается **один раз после цикла**. Квадратичного повторного расширения таблицы здесь нет.

Но на коротких C++ запусках заметными могут стать `R` созданий индексов, блоков и служебных объектов pandas. Можно вынести существующее формирование одной записи в общую внутреннюю функцию; публичный `runTest` продолжит оборачивать одну запись в DataFrame, а `runTests` соберёт список записей и создаст таблицу один раз. Дублировать логику запуска subprocess и извлечения метрик нельзя.

Итоговое хранение `Θ(RW)` необходимо по контракту «вернуть все исходные результаты». Нельзя обещать `O(1)` памяти без изменения этого контракта. Аналогично, копирование списков флагов на границе mutable-generator нужно для корректности и отдельно покрыто тестами; его нельзя полностью убирать ради небольшого выигрыша.

### P6. Подготовка графика копирует лишние данные и многократно сортирует строки

**Код:** [plotDf = df.copy](/Users/user/Code/Repos/GraphDrawing/gd_experiments.py:546), [sns.lineplot для одной метрики](/Users/user/Code/Repos/GraphDrawing/gd_experiments.py:565), [цикл всех метрик](/Users/user/Code/Repos/GraphDrawing/gd_experiments.py:577).

Для графика нужны `run` и выбранные числовые столбцы, но копируется весь DataFrame, включая stdout, stderr, пути и флаги. Это лишнее `O(RW)` копирование табличных блоков/ссылок. Важно: `df.copy()` не выполняет рекурсивное глубокое копирование каждого списка флагов внутри object-ячейки. Размер содержимого этих списков нельзя ещё раз безусловно прибавлять как глубокую копию.

`sns.lineplot` вызывается с `estimator=None, errorbar=None`, но без `sort=False`. В установленном Seaborn 0.13.2 сортировка включена по умолчанию; `_LinePlotter.plot` вызывает `sort_values` для x и y. Для десяти метрик это десять отдельных сортировок. Консервативная верхняя оценка подготовки — `O(kR log R)` помимо копий и преобразования столбцов; конкретная реализация сортировки может быть быстрее на уже упорядоченных входах.

Для результата `runTests` уникальные `run` уже идут по возрастанию: достаточно взять нужные столбцы и отключить сортировку. Получится `O(kR)` подготовки. Для произвольной таблицы с уникальным `run` можно один раз отсортировать по нему и также передавать `sort=False`: `O(R log R+kR)`.

Если `run` повторяются, Seaborn сортирует ещё и по значению конкретной метрики. Одна общая сортировка по `run` может изменить порядок соединения точек. Поэтому быстрый путь надо ограничить уникальными номерами либо явно сохранить/переопределить политику повторов. Rasterization, подписи и размер изображения в эти оценки подготовки не входят.

### P7. Отдельный объект Matplotlib для каждого ребра

**Код:** [Poincaré-дуги](/Users/user/Code/Repos/GraphDrawing/render.py:147), [3D-линии](/Users/user/Code/Repos/GraphDrawing/render3d.py:101).

В Poincaré-ветке каждое ребро создаёт свою полилинию из `s` точек и отдельный `Line2D` через `ax.plot`. В 3D каждое ребро аналогично создаёт отдельный объект линии. Помимо необходимых координат появляется `Θ(M)` полноценных объектов Matplotlib с собственной обработкой свойств, границ и рисования.

Все 2D-полилинии можно передать одной `LineCollection`, а 3D-отрезки — `Line3DCollection`. Геометрия останется `Θ(Ms)` в Poincaré и `Θ(M)` в 3D; число контейнеров линий станет постоянным. Это сокращение накладных расходов, а не переход к `O(1)` времени или общей памяти рендера. При пакетной подготовке можно временно иметь и список исходных координат, и массив коллекции — пик памяти следует контролировать.

Нужна визуальная проверка порядка рисования, прозрачности, толщины, границ осей и 3D-проекции. Метки вершин остаются `Θ(N)` текстовых объектов, потому что они входят в текущий рисунок; их удаление было бы изменением требований к изображению. Для обычных прямых рёбер 2D код уже использует `nx.draw_networkx_edges`, и переносить туда диагноз «по одному ax.plot на ребро» нельзя.

### P8. Квадратичный генератор G(n,p) при малом p

**Код:** [gen1](/Users/user/Code/Repos/GraphDrawing/gen.py:31). Проверены реализации NetworkX 3.6.1 в локальной среде: [gnp_random_graph](/Users/user/Code/Repos/GraphDrawing/.venv/lib/python3.14/site-packages/networkx/generators/random_graphs.py:122) и [fast_gnp_random_graph](/Users/user/Code/Repos/GraphDrawing/.venv/lib/python3.14/site-packages/networkx/generators/random_graphs.py:41).

При `0<p<1` обычный генератор проходит по всем неупорядоченным парам вершин: `Θ(N²)` даже когда ожидается только `O(N)` рёбер. `fast_gnp_random_graph` пропускает серии отсутствующих рёбер и генерирует то же распределение G(n,p) за `O(N+𝔼[M])` в среднем. Это сохранение вероятностной модели, без смены модели графа или алгоритма его раскладки.

При `p=Θ(1/N)` ожидаемая работа становится линейной. При постоянном ненулевом `p` число рёбер само `Θ(N²)`, поэтому улучшения порядка нет. Текущий стандартный `p=0.1` и вызов `SmallGraph` с `p=0.7` относятся именно ко второму случаю, а `p=0`/`p=1` в библиотеке обрабатываются отдельно.

Одинаковый seed у двух реализаций не означает одинаковый конкретный граф: последовательность потребления случайных чисел отличается. Для уже зафиксированных датасетов их не следует незаметно перегенерировать. Кроме того, `gen1` всё равно запускает `spring_layout`, поэтому изменение генератора само по себе не гарантирует ускорения **всего** gen1 до линейного — следующий пункт описывает этот отдельный расход.

### P9. Генерация датасета безусловно включает дорогую визуализацию

**Код:** [gen1: spring_layout и PNG](/Users/user/Code/Repos/GraphDrawing/gen.py:34), [gen2: spring_layout и PNG](/Users/user/Code/Repos/GraphDrawing/gen.py:63).

Чтобы записать вершины и рёбра в dataset JSON, координаты NetworkX не нужны. Но обе функции безусловно сначала вычисляют раскладку и рисуют подписанный PNG. Если задача генерации — подготовить много графов для C++ экспериментов, это лишняя полная стадия `L_NX+V_PNG` на граф.

Достаточно явного режима генерации без preview, сохранив текущий режим с изображением. В этом режиме после генерации графа остаётся `Θ(N+M)` формирования записи. Это не предложение заменить или «ускорить» сам FaR, а возможность не запускать визуализацию там, где её результат не используется.

Если PNG является требуемым результатом, расход не лишний и этот пункт неприменим. Нельзя автоматически описывать текущий `nx.spring_layout` как всегда одну force-реализацию: в установленной NetworkX 3.6.1 стандартный `method='auto'` выбирает `force` ниже 500 вершин и `energy` начиная с 500. Поэтому в таблице используется `L_NX`, а не необоснованная единая формула по `T` для всех входов.

## Что проверено и сознательно не объявлено проблемой

1. **Квадратичные основные переборы.** Точное отталкивание FaR, подсчёт всех пересечений и общий проход для min/max/**среднего** расстояния между вершинами не названы сами по себе дефектами. Barnes–Hut, sweep line, пространственные индексы и приближённые метрики здесь не предлагаются: это отдельный алгоритмический проект. В частности, k-d tree для ближайшей пары не устраняет текущий расчёт среднего расстояния по всем парам.
2. **Выходной writer.** [EmbeddingWriter](/Users/user/Code/Repos/GraphDrawing/src/io/EmbeddingWriter.cpp:19) пишет данные потоково, получает координаты и рёбра по ссылкам и не строит выходной DOM. Для реально поддерживаемого 2D/3D формата время `Θ(N+M+f)`, дополнительная память не пропорциональна всему output. Если обобщать формат на произвольное число координат, естественная оценка записи была бы `Θ(Nf+M)`, но сейчас writer выводит только x/y и опционально z.
3. **Граф и возвращаемые значения.** [Graph::addEdge](/Users/user/Code/Repos/GraphDrawing/src/core/Graph.cpp:23) делает амортизированно постоянные вставки. Отсутствие `reserve` само по себе не превращает построение графа в `Θ(M²)`. Обычные возвраты локального `vector`/`Graph` используют move/NRVO; они не приравнивались к заведомо глубоким копиям. `_graph` в `Embedding` — ссылка, а не собственная копия графа.
4. **Python scoring.** `scoreRuns` нормализует каждый используемый столбец один раз: `O(RW+kR)` с копированием результата. `bestRun` использует `idxmax` за `O(R)`, а не сортирует все строки. Копия `scoreRuns` поддерживает явно заявленное поведение «исходный DataFrame не изменяется», поэтому её простое удаление некорректно. `runTests` уже имеет один финальный concat.
5. **Флаги и метаданные.** Повторные `flagValue` и копии CLI-списков — линейные по небольшому числу токенов, без скрытого квадратичного цикла в текущем коде. Копии на границе callback сохраняют mutable-generator семантику. Генерация строки `--S` длины `d` в ноутбуке стоит `Θ(d)`, что соответствует размеру требуемого ввода.
6. **Fallback рендереров.** `load_edges_from_dataset` действительно разбирает весь датасет, однако стандартный C++ output уже содержит `edges`, поэтому этот путь при обычном `renderRun` не включается. Для старых JSON без рёбер применимы идеи C11/P1. Это условный путь, а не дополнительный обязательный разбор датасета при каждом рендере.
7. **Ноутбуки и актуальность пути.** `metrics_from_dim.ipynb` использует текущие `runTest/runTests` и потому покрывается найденными активными проблемами. `test.ipynb`, `test2.ipynb`, `far_test.ipynb`, `far_test copy.ipynb`, `networkx_comp.ipynb` импортируют удалённые `runGd`, `bestOfN`, `appendLogRow` и другие имена; на чистом ядре их импорт не соответствует текущему модулю. `FaR_versions_comp.ipynb` не содержит существенного исполняемого пайплайна. В `networkx_comp` есть повторный deterministic `spring_layout(seed=1543)` при разных запусках `mainTest`; кеш baseline был бы полезен после миграции ноутбука, но это не подтверждённая текущая runtime-проблема. Старые сохранённые outputs не использовались как доказательство актуальной производительности.
8. **Границы корректности.** Reader определяет `N = max(vertex_id)+1`, а не количество перечисленных ID. Разреженные внешние ID могут искусственно увеличить все следующие стадии, но сжатие ID меняет трактовку отсутствующих номеров и формат идентификаторов; без определения контракта это не безопасная оптимизация того же результата. Аналогично, исправление евклидовых расстояний для Poincaré или дефектов обработки петель — отдельные изменения корректности.
9. **Сборка и завершение ресурсов.** Текущий `build/CMakeCache.txt` содержит `CMAKE_BUILD_TYPE=Debug`; `compileGd` не включает Release. Это может существенно влиять на абсолютное время, но не является асимптотическим дефектом. Обе CLI-функции рендера закрывают свои Figure; функции `displayTwo`/`plotMetrics` возвращают Figure вызывающему коду. Считать их безусловной утечкой нельзя: удержание зависит от владельца и notebook backend. Запущенные для аудита процессы завершены.

## Предлагаемый порядок исправлений

Сначала C2+C3+C4: один расчёт метрик на камеру, обработка координат кандидатов по одному и ссылки внутри Metrics. Это наиболее заметное сочетание для `kleinBestView`, причём выигрыш C2 уменьшает число повторений всех остальных расходов Metrics. Параллельно по смыслу, но независимо в реализации, C1 устраняет кубическую стадию при переборе больших размерностей с `poly`.

Затем C6 и локальные части C8–C10: повторное использование `disp`, отсутствие временных векторов масштабирования, один расчёт угла и подготовка неизменных данных ребра. C5 дополняет их уменьшением копирований на границах стадий. Более широкий API подготовленной геометрии C7/C9 стоит вводить после измерения этих простых исправлений.

В Python на больших датасетах первыми важны P1/P2; на длинных дешёвых сериях — P3–P6; при массовом построении PNG — P7. P8/P9 относятся к подготовке новых датасетов и применяются в оговорённых режимах. Для проверки будущих исправлений нужны сравнения метрик, выбранной камеры и координат при фиксированных seeds, а для рендера — проверка изображений; чистый speed benchmark без проверки результатов недостаточен.
